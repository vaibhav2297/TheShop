# Architecture guidance

Read for C# or layer decisions. Constitution owns numbered requirements; use existing nearby implementation as pattern.

| Layer | Placement |
|---|---|
| Domain | `Entities/`, `ValueObjects/`, `Enums/`, `Exceptions/` |
| Application | `Features/<Capability>/Commands/<Command>/`, `Queries/<Query>/`, shared `DTOs/`; external interfaces under `Common/Interfaces/` |
| Infrastructure | Database `Persistence/Records/`, `Mappers/`, `Repositories/`; SDK adapters under `Auth/`, `Payments/`, `Email/`, `Storage/` |
| Web | `Pages/`, `Components/`, `State/`, `Services/`, `Theme/`, `Resources/`, `Common/`, `Styles/` |

`Persistence/` root holds cross-cutting database plumbing. Feature-specific database helpers use purpose-named subfolders. Storage adapters belong under `Storage/`; never create `Infrastructure/<Feature>/`.

Reuse `Result<T>`, MediatR validation/authorization pipeline, `ICurrentUserService`, mappings, repository interfaces, and DI extensions. Inspect actual APIs before using them; examples are not contracts. Validators check input; entities enforce invariants; handlers translate expected domain rejection using established project pattern.

Persistence uses internal record/mapping/repository separation. SDK-shaped models do not cross adapter boundary. Match existing DI lifetimes and mappings. Admin/customer operations share handlers where behavior matches; permission differences do not justify duplicated business logic.

Use file-scoped namespaces, one primary class per file, names matching folders. Commands/queries/DTOs are records. Name interfaces `I...`, DTOs `...Dto`, persistence records `...Record`. Async I/O names end in `Async`, except required interface conventions such as MediatR `Handle`.

Enable nullable references. Use `!` only with proof. Prefer primary constructors for dependency storage; explicit constructors for validation, subscriptions, or composition. Prefer collection expressions where target type is known.

Public XML summaries describe intent, constraints, and observable effects. Add `param`, `returns`, and `exception` only when informative. Leave autogenerated files untouched. Ordinary comments explain non-obvious implementation details.

When changing resource-key producers, inspect current shared/generated key mechanism. Do not copy Web resource classes into Application or invent resource wiring. Keep UI state, URLs, and busy indicators outside Domain/Application.
